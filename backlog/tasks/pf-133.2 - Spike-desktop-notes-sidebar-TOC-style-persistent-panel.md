## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Explore replacing the desktop notes FAB/popover with a persistent sidebar panel (like the existing TOC sidebar on the right). Notes would be inline and always visible during a bake, rather than hidden behind a floating button.

**Questions to explore:**
- Can notes and TOC coexist as sidebars? (left notes, right TOC?)
- Or should notes replace TOC context-sensitively during active bakes?
- How does the sidebar layout shift when notes are open vs closed?
- Does the inline note approach change how per-step notes are captured? (sidebar shows all step notes in a scrolling list vs per-step popovers)

**Context from PF-133:**
- Current desktop: FAB bottom-left opens overlay panel
- Current mobile: same FAB pattern (this stays — mobile has no room for sidebar)
- TOC sidebar pattern: right-side, border-left, text-only, auto-expands on click

**Not part of PF-133 scope** — this is a follow-up exploration for the notes UX on desktop only.

# PF-133.2 Research Findings: Desktop Notes Sidebar

## AC1: Layout Research — Three Options Evaluated

### Current Layout Baseline

The recipe page uses `max-w-4xl` (896px) centered with `mx-auto` and `px-4` (16px padding each side). Inside that, the recipe content area uses `md:flex md:gap-6`:

- **Content column**: `flex-1 min-w-0` (takes remaining space)
- **TOC sidebar**: `w-[160px] flex-shrink-0`, `sticky top-20`, `hidden md:block`

At the `md` breakpoint (768px), the sidebar becomes visible. With 32px horizontal page padding and 24px gap:

- Available content width at 768px: `768 - 32 (px-4) = 736px` usable inside `<main>`
- With TOC: `736 - 160 (sidebar) - 24 (gap) = 552px` for recipe content
- At wider screens (896px max-w): `896 - 32 - 160 - 24 = 680px` for recipe content

---

### Option 1: Left Sidebar (Notes) + Right Sidebar (TOC)

**Concept**: Notes sidebar on the left (always visible during bake), TOC stays on the right. Content sandwiched between two sidebars.

**Pros**:
- Clear separation of concerns: navigation (right) vs. data capture (left)
- Notes are always visible — no toggling, no missed observations
- Mirrors common IDE layout (file tree left, outline right)
- Both sidebars use the same visual language (border-l/border-r, sticky, text-only)

**Cons**:
- **Content width loss is severe at md breakpoint** (see AC3 for math)
- Two sidebars + content requires wider viewport to be usable; effectively needs `lg` breakpoint (1024px)
- Visual balance may feel cramped — recipe cards already have internal padding
- App.vue layout would need significant restructuring (currently assumes single sidebar)
- Three-column layout is unusual for a cooking app — may feel like an admin dashboard

**Implementation complexity**: Medium-high. Requires new layout wrapper, new breakpoint logic (sidebar appears at lg instead of md), and responsive fallback.

---

### Option 2: Single Sidebar with Tabs (Notes/TOC Toggle)

**Concept**: Replace TocSidebar with a tabbed sidebar on the right. Two tabs: "Contents" (current TOC) and "Notes" (scratchpad). Only one active at a time.

**Pros**:
- **Zero additional content width loss** — same 160px footprint as current TOC
- Minimal layout changes — same flex container, same position
- Tab UI is familiar (browser tabs, editor tabs)
- Notes get sidebar's persistent visibility without dual-sidebar cost
- Natural evolution of TocSidebar — add capability without new component
- Shares existing visual language exactly (border-left, text-only, stone palette)

**Cons**:
- User cannot see TOC and notes simultaneously
- Tab switching adds friction during active baking (one more tap to check position)
- 160px width is tight for note content (textarea, ratings, timestamps)
- Notes section needs more vertical space than TOC — may scroll heavily
- Mental model shift: sidebar changes purpose based on tab, which can be disorienting

**Implementation complexity**: Low-medium. Extend TocSidebar with a tab strip at top, conditionally render TOC nav or notes panel. Same container, different content.

---

### Option 3: Collapsible Left Panel

**Concept**: Notes live in a collapsible panel on the left side. Collapsed state shows a thin strip (24-32px) with an icon/badge; expanded state shows full notes panel (240-280px). TOC remains on the right unchanged.

**Pros**:
- Notes visible on demand without covering content
- Collapsed state takes minimal space (effectively ~32px, similar to a margin)
- Expanded state gives more room than 160px for note content (rich inputs, ratings)
- TOC remains always-visible — no tradeoff between navigation and notes
- Familiar pattern (VS Code sidebar, Figma panels, Notion)
- Badge on collapsed strip shows note count — maintains awareness

**Cons**:
- Content area width shifts when panel opens/closes (layout jank unless animated)
- At md breakpoint, expanded panel + TOC still squeezes content (see AC3)
- Requires animation/transition work for smooth collapse
- Two different sidebar widths on screen simultaneously looks asymmetric
- More complex state management (open/closed, remembered per session)

**Implementation complexity**: Medium. New component for collapsible panel, CSS transition for width change, state persistence in localStorage.

## AC3: Content Width Impact at md Breakpoint (768px)

### Current Layout (single right sidebar)

| Component | Width |
|-----------|-------|
| Viewport | 768px |
| Page padding (px-4 × 2) | 32px |
| max-w-4xl cap | 896px (not active at 768px) |
| Usable inside main | 736px |
| TOC sidebar (w-[160px]) | 160px |
| Gap (gap-6 = 24px) | 24px |
| **Recipe content** | **552px** |

552px is comfortable for recipe cards.

### Option 1: Dual Sidebars (left notes + right TOC)

Assuming notes sidebar at 160px (matching TOC):

| Component | Width |
|-----------|-------|
| Usable inside main | 736px |
| Left notes sidebar | 160px |
| Right TOC sidebar | 160px |
| Two gaps (24px × 2) | 48px |
| **Recipe content** | **368px** |

**RED FLAG: 368px is well below the 480px usable minimum.** Recipe cards have internal padding (~32px), leaving ~336px for text. Step directions would line-wrap excessively. StageCard headers with checkboxes + scratchpad icons would overflow. This option is NOT viable at the md breakpoint.

Even with narrower 120px sidebars: `736 - 120 - 120 - 48 = 448px` — still below 480px.

**Dual sidebars require lg breakpoint (1024px) minimum**: `1024 - 32 - 160 - 160 - 48 = 624px`. That's workable but means md viewport (768-1023px) falls back to no sidebars or single sidebar only.

### Option 2: Tabbed Sidebar (same footprint)

| Component | Width |
|-----------|-------|
| Same as current | Same as current |
| **Recipe content** | **552px** |

**No impact.** Identical to current layout.

### Option 3: Collapsible Left Panel

Collapsed (32px strip): `736 - 32 - 160 - 48 = 496px` — just above 480px minimum. Tight but workable.

Expanded (260px panel): `736 - 260 - 160 - 48 = 268px` — **not viable at md breakpoint**.

At lg (1024px) expanded: `1024 - 32 - 260 - 160 - 48 = 524px` — workable.

### Summary Table

| Option | Content Width @ 768px | Content Width @ 1024px | Verdict |
|--------|----------------------|----------------------|---------|
| Current (TOC only) | 552px | 680px | Baseline |
| Dual sidebars | 368px | 624px | FAILS md, OK at lg |
| Tabbed sidebar | 552px | 680px | No change |
| Collapsible (closed) | 496px | 632px | Marginal at md |
| Collapsible (open) | 268px | 524px | FAILS md, OK at lg |

## AC4: Step-Note Integration — Two Interaction Models

### Current State

Per-step notes use `ScratchpadNote.vue` — a small `StickyNote` icon (28×28px) rendered inline next to each step title in `StateStep.vue`. Clicking opens a positioned popover with:
- Existing entries for that step
- Prompted reminder questions
- Quick rating buttons (good/ok/bad)
- Freeform textarea

The icon shows an accent-colored badge with entry count when entries exist.

### Model A: Step Icon Scrolls Sidebar to That Step's Notes

**Behavior**: The per-step `StickyNote` icons remain in place. Clicking one:
1. Opens the sidebar notes panel (if tabbed variant, switches to Notes tab)
2. Scrolls the sidebar to that step's entry group
3. Focuses the text input for that step
4. Highlights the step group in the sidebar (accent border-left or background tint)

**Pros**:
- Keeps the spatial affordance — users see exactly which steps have notes at a glance
- Badge count per step preserved
- Sidebar provides more room than a popover for reviewing/entering notes
- No popover occlusion of recipe content
- Works well with tabbed sidebar (Model A icon click = switch to Notes tab + scroll)

**Cons**:
- Two UI elements for the same concept (icon in content + section in sidebar) — may confuse
- Sidebar must maintain scroll position per step, which is state to manage
- If sidebar is narrow (160px), note entry area is still cramped
- Requires sidebar to be open/visible — if collapsed or on Notes tab, icon click must trigger open

**Best paired with**: Tabbed sidebar (Option 2) or collapsible panel (Option 3)

### Model B: Step Icons Removed, Sidebar Shows All Notes in Order

**Behavior**: Remove `ScratchpadNote.vue` icons from `StateStep.vue`. The sidebar notes panel shows a chronological or step-ordered feed of all entries. Users add notes by:
1. Scrolling to the step section in the sidebar
2. Or using a "quick add" input at the top of the sidebar with a step selector dropdown

**Pros**:
- Cleaner step UI — no icons cluttering the step title row
- Single source of truth for notes (sidebar only)
- All notes visible in one scrollable feed — good for reviewing bake progress
- Simpler mental model: "notes are in the sidebar"

**Cons**:
- **Loss of spatial context** — you cannot see at a glance which steps have notes
- No badge counts on individual steps — awareness drops significantly
- Requires step selector dropdown (extra interaction) to attach notes to specific steps
- Users must scroll sidebar to find the right step — friction for mid-bake note taking
- Removes one of the strongest affordances from PF-133: the inline icon that says "this step has data captured"

**Risk**: This degrades the per-step annotation UX that was specifically chosen in PF-133.1's demo review. The inline icon was selected over FAB-only because it provides zero-friction per-step context.

### Model C (Hybrid — Recommended): Icons as Indicators, Sidebar as Editor

**Behavior**: Keep per-step icons as read-only indicators (badge count, accent color when notes exist). Clicking the icon scrolls the sidebar to that step AND opens the sidebar if needed. All actual editing happens in the sidebar panel. The popover is eliminated.

This combines Model A's spatial awareness with Model B's single-editor principle.

## AC5: Mobile Exclusion Confirmed

### TocSidebar Mobile Pattern

`TocSidebar.vue` uses `hidden md:block` on the desktop sidebar `<aside>` element (line 81). Below the `md` breakpoint (768px), the sidebar is completely hidden. A separate FAB button (`md:hidden fixed bottom-4 right-4`) opens a bottom sheet via Teleport.

### GeneralNotesFab Mobile Pattern

`GeneralNotesFab.vue` already has dual FAB buttons:
- Desktop: `md:fixed md:bottom-4 md:left-4 hidden md:flex` (line 77)
- Mobile: `md:hidden fixed bottom-4 left-4` (line 92)

Both use Teleported overlay panels.

### Confirmation

Any sidebar implementation would follow the same pattern:
- Desktop (`≥768px`): Sidebar visible, FAB hidden
- Mobile (`<768px`): Sidebar hidden (`hidden md:block`), existing FAB pattern unchanged

The mobile notes FAB (bottom-left, `GeneralNotesFab.vue`) and mobile TOC FAB (bottom-right, `TocSidebar.vue`) would continue to coexist as they do today. No changes to mobile UX.

## AC6: Decision Recommendation

**Recommended approach: Option 2 — Single Sidebar with Tabs (Notes/TOC Toggle)**

The tabbed sidebar is the clear winner for three reasons. First, it has zero content width impact — it reuses the existing 160px sidebar footprint, which means it works at the md breakpoint (768px) without any layout changes or breakpoint gymnastics. The dual-sidebar options (1 and 3) both fail at md and require pushing sidebar visibility to lg (1024px), which means a significant portion of tablet and small laptop users lose the sidebar entirely. Second, it has the lowest implementation complexity — TocSidebar.vue already exists with the exact visual language needed (border-left, sticky, stone palette, hidden md:block, mobile bottom sheet). Adding a tab strip and conditionally rendering TOC nav vs. notes panel is a contained change to one component, not a layout restructuring. Third, it aligns with the project's design philosophy of minimal UI surface area — one sidebar that serves two purposes is more "coder meets baker" than a three-column dashboard layout. The main tradeoff (cannot view TOC and notes simultaneously) is acceptable because during active baking, the user is focused on the current step and notes; TOC navigation is an occasional action, not a continuous need. The step-note integration should use Model C (icons as indicators, sidebar as editor) to preserve the spatial awareness from PF-133 while centralizing editing in the sidebar.
