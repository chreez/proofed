# PF-255.3 Spike Notes — Throughput modeling

**Status:** Findings drafted; awaiting user sign-off (per `.claude/rules/grooming.md` Spike Completion Requirements). Spike status remains `In Progress`.

**Date:** 2026-05-12

---

## 1. Background

PF-255 (Pricing, throughput, and bake schedule planner) needs to model a baker's day: how long does any given recipe occupy the baker (hands-on), the kitchen (passive proof), and the oven (the scarce resource)? Today the only timing field on a recipe is `meta.total_time: string` — a free-form human label like `"~5 hrs (1.5 active)"` that the scheduler can't reason about.

This spike walks the existing recipe corpus to:

1. Demonstrate that per-state `duration_min` + `timer` can be decomposed into `prep_active_min` / `proof_passive_min` / `oven_occupancy_min` with simple heuristics.
2. Propose four optional numeric fields on `RecipeMeta` that capture the decomposition, side-by-side with the existing string for backward compat.
3. Map the existing `meta.yields` / `config.stats` shape onto the "oven slot" abstraction the scheduler needs.

No `src/` code is changed.

---

## 2. Classification heuristic

Each `RecipeState` is classified into one of four buckets by walking `stages[].states[]` and inspecting `state.id`, `state.title`, `state.timer`, and the parent stage id:

| Bucket | Predicate | Counts toward |
|---|---|---|
| `oven_occupancy` | `'preheat'` in title/id; OR stage id contains `'bake'` AND title/id contains `'bake'` | `oven_occupancy_min`, `bake_min` |
| `passive_cool` | title/id contains `'cool'` | (separate — oven is freed) |
| `passive_proof` | `timer: true` AND not bake-stage; OR id contains `cold_bulk_ferment` / `cold_proof` / `cold_retard` (regardless of `timer` flag — see §6 ambiguities); OR id/title contains `chill` / `rest` / `ferment` / `proof` / `autolyse` / `retard` / `temper` with `timer: true` | `proof_passive_min` |
| `active` | default fallthrough — `timer: false` and not in any of the above | `prep_active_min` |

Heuristic is intentionally simple so the schema can be backfilled mechanically; humans audit edge cases (see Draft 1 below).

## 3. Recipe time decomposition table (5 audited recipes)

| Recipe | yields | meta.total_time (current string) | prep_active_min | proof_passive_min | oven_occupancy_min | bake_min | passive_cool_min | sum |
|---|---|---|---:|---:|---:|---:|---:|---:|
| ATK Cinnamon Buns Ultimate | 8 buns | `~5 hrs (1.5 active)` | 52 | 180 | 52 | 52 | 30 | 314 |
| Jalapeño Cheddar Sourdough | 2 loaves (~730g each) | `~26 hrs (1 hr active, 25 hrs passive)` | 85 | 1160 | 98 | 98 | 60 | 1403 |
| Sourdough Chocolate Chip Cookies | ~22-24 cookies | `~17 hrs (30 min active Day 1, …)` | 26 | 1020 | 29 | 29 | 15 | 1090 |
| NY-Style Pizza Dough | 2 pizzas | `~3 days (45 min active)` | 37 | 3750 | 55 | 55 | 3 | 3845 |
| Sourdough Cheddar Bay Biscuits | ~10 biscuits | `~30 min (20 min active, 12-15 min bake)` | 16 | 0 | 19 | 19 | 0 | 35 |

Notes:

- **`bake_min == oven_occupancy_min` for all five recipes.** All five are single-bake recipes (one preheat → one bake). For multi-bake recipes (e.g. baking two cookie sheets sequentially) the two fields diverge — `bake_min` is per-batch active oven time, `oven_occupancy_min` is the recipe's total oven-slot footprint. See §5.
- **Cool time is intentionally separate** (`passive_cool_min`). Once the oven door opens to pull the bake, the oven is freed for the next slot — cool happens on a rack and does not block the scarce resource. We do **not** propose adding it to the schema in this pass; the scheduler can treat it as ignorable.
- **Active time vs `meta.total_time` parentheticals match within ~30%.** ATK reads "1.5 active" → computed 52 min = 0.87 hr (delta is mostly assembly/glaze authoring style — the human estimate rounds up). Sourdough Cheddar Bay Biscuits reads "20 min active" → computed 16 min (close). Pizza reads "45 min active" → computed 37 min (close). Cookies reads "30 min Day 1 + 30 min Day 2 = 60" → computed 26 min (under — likely doesn't account for cleanup / portioning lag). The heuristic captures the bulk; humans should still review backfilled values once.
- **Total times reconcile with `meta.total_time` headline numbers.** ATK 314 min ≈ 5.2 hr ✅. Sourdough 1403 min ≈ 23.4 hr (string says ~26 hr — gap is informal padding around overnight cold retard). Cookies 1090 min ≈ 18 hr (string ~17 hr ✅). Pizza 3845 min ≈ 64 hr ≈ 2.7 days (string ~3 days ✅). Biscuits 35 min (string ~30 min ✅).

## 4. Proposed RecipeMeta schema additions

Read existing interface at `/Users/chris/workspace/proofed/src/types/recipe.ts:161-181`.

Additions are **all optional** and **additive only** — `total_time: string` stays as the canonical human-facing label, and any of these four numeric fields may be absent on a recipe (scheduler falls back to "unknown duration → use cumulative state sum or skip in throughput math").

```diff
 export interface RecipeMeta {
   name: string
   /**
    * Short display name for compact contexts (IG share captions, etc.).
    * When absent, callers fall back to stripping ' - {variant}' from `name`.
    */
   shortName?: string
   source?: RecipeSource
   yields: string
   total_time: string
+  /**
+   * Hands-on baker time, in minutes. Sum of states whose `timer` is false
+   * (mixing, shaping, scoring, glazing, etc.). Excludes passive rises and
+   * oven time. Optional — scheduler treats `undefined` as "not yet
+   * decomposed" and falls back to summing per-state durations.
+   * (PF-255.3)
+   */
+  prep_active_min?: number
+  /**
+   * Passive kitchen time, in minutes. Sum of states with `timer: true` that
+   * are NOT bake-stage states — rises, autolyses, bench rests, cold
+   * retards, chill steps. Baker is free; oven is free. (PF-255.3)
+   */
+  proof_passive_min?: number
+  /**
+   * Total minutes the oven slot is occupied by this recipe, summed across
+   * all preheat + bake states. For multi-batch recipes (e.g. two cookie
+   * sheets baked sequentially) this is the *total* slot footprint, not the
+   * per-batch duration. See `bake_min` for per-batch oven time. (PF-255.3)
+   */
+  oven_occupancy_min?: number
+  /**
+   * Single-batch active oven time, in minutes. For single-bake recipes,
+   * equals `oven_occupancy_min - preheat_min`. For multi-batch recipes
+   * (cookies in N sheet rounds), the per-batch bake. The scheduler uses
+   * this to interleave batches with other recipes. (PF-255.3)
+   */
+  bake_min?: number
   description?: string
   allergenOverride?: string[]
   outdated?: OutdatedMarker
   shopping_notes?: string
 }
```

### Field rationale

- **Why optional, not required?** Backfilling 26 recipes is mechanical but the heuristic still produces ambiguous cases (§6). Required fields would either force the backfill to commit to ambiguous values or block the schema change. Optional fields let us roll out the scheduler against the recipes that *are* annotated and degrade gracefully on the rest.
- **Why minutes and not hours?** Existing `RecipeState.duration_min`, `BakePhase.duration_min`, and `ProofPhase.duration_min` are all in minutes. Stays consistent.
- **Why keep `total_time: string` instead of deprecating?** The string is read by recipe-card UI and surfaces context that the numeric breakdown doesn't ("~3 days" reads better than "3845 minutes"). Treat it as a human caption; the new fields are machine inputs.
- **Why split `bake_min` from `oven_occupancy_min`?** A scheduler that allocates oven slots needs to know both: total slot footprint (does this recipe collide with another bake on the same day?) AND per-batch length (can I slot a quick biscuit batch between two cookie rounds?). For single-bake recipes they're equal and the user can omit one — same trick as `nutrition.totals` vs `perServing`.

### Open question (defer to PF-255.4 design)

Do we also need `preheat_min`? Right now it's folded into `oven_occupancy_min`. If the scheduler wants to plan "preheat starts at 9:45 so the bake at 10:00 is hot" then yes. If it just allocates "oven busy 9:45-11:00" then no. The five-recipe audit shows preheat ranges from 15 min (cinnamon buns) to 50 min (sourdough), so it's a meaningful chunk to split out. Recommend deferring until the scheduler UI design (PF-255.4) decides whether preheat is a separately movable block.

## 5. Yield → oven slot throughput mapping

The scheduler needs to convert `meta.yields` ("8 buns", "2 loaves", "~22-24 cookies") into oven-slot occupancy. The kitchen abstraction:

> **A single home oven is one slot.** It can hold N items per batch (limited by pan size), and recipes that yield more than N items per batch are baked in K sequential batches. Each batch = one slot-occupancy interval of `bake_min`.

### The `config.stats` block already has the structural data we need

From the corpus survey (26 non-index recipes):

- **19/26 recipes** already have `config.stats` with `{ defaultYield, unit, servingsPerItem }`. Example: `atk-cinnamon-buns-ultimate.json` → `defaultYield: 8, unit: 'buns', servingsPerItem: 1`.
- **7/26 recipes** are missing the `stats` block: `ba-bolognese`, `jalapeno-cheddar-sourdough`, `sourdough-chocolate-chip-cookies`, `sourdough-discard-cheese-crackers`, `tartine-lemon-cream-tart`, `tartine-rugelach`, plus implicit gaps elsewhere. Backfill candidate (see Draft 2).

### Proposed mapping (no schema change required for this part — uses existing fields)

For a recipe with `config.stats.defaultYield = Y` and a (new, optional) `config.stats.itemsPerBatch = B`:

```
batches_needed = ceil(Y / B)
total_slot_time = batches_needed * bake_min + preheat_min  (preheat once, shared across batches)
```

Worked examples from the five audited recipes:

| Recipe | yields (Y) | items_per_batch (B) | batches | preheat | per-batch bake | total slot time |
|---|---:|---:|---:|---:|---:|---:|
| ATK Cinnamon Buns | 8 buns | 8 (one cast-iron skillet) | 1 | 15 | 37 | 52 min |
| Jalapeño Cheddar Sourdough | 2 loaves | 1 (one dutch oven) | 2 | 50 | 48 | 50 + 96 = 146 min ⚠ |
| Sourdough Choc Chip Cookies | 24 cookies | 8 (per sheet pan) | 3 | 15 | 14 | 15 + 42 = 57 min |
| NY-Style Pizza | 2 pizzas | 1 (one baking steel) | 2 | 45 | 10 | 45 + 20 = 65 min |
| Sourdough Cheddar Bay Biscuits | 10 biscuits | 10 (one sheet) | 1 | 5 | 14 | 19 min |

⚠ **The sourdough loaf case shows the second-bake reheat caveat.** Bake-1 ends, you pull the dutch oven, reset it back into the oven covered, and the oven recovers heat in 5-10 min before loading bake-2. Real-world scheduling needs a `recovery_min` between sequential batches for high-temp recipes. Defer to PF-255.4 design.

### Why `itemsPerBatch` isn't on `meta` and would live on `config.stats`

`config.stats` is already the "structural shape of a yield" container (`defaultYield`, `unit`, `servingsPerItem`). Adding `itemsPerBatch` there keeps semantic cohesion: `meta.yields` is a human string, `config.stats.*` is structured throughput data. Not in scope for this spike to make the change — flagged as Draft 3.

### Edge cases the scheduler needs to handle

1. **Ranges in yields** ("~22-24 cookies", "2-3 baguettes"). `defaultYield` already resolves these to a single number — good.
2. **No `stats` block at all.** Scheduler should treat recipe as "unknown throughput → assume 1 batch, surface a warning in the UI."
3. **Multi-pan recipes that share an oven slot.** Two sheet pans of cookies can stack on two racks → effectively `itemsPerBatch * 2` per slot occupancy. Whether the recipe says "stagger" or "bake side-by-side" matters. Recommend a free-form `state_notes` rather than schema for the first pass.
4. **Recipes with multiple distinct bake stages.** None of the five audited has more than one bake stage today, but e.g. a tart with blind-bake + final-bake would. Out of scope for first scheduler MVP.

## 6. Ambiguities flagged during classification

Cases where the heuristic in §2 produced a result a human should verify:

- **`ny-style-pizza.json:COLD_BULK_FERMENT` (720 min, `timer: false`)** — clearly a 12-hour passive fridge rest, but the JSON has `timer: false`. The classifier overrode this based on the `cold_bulk_ferment` id. Either the JSON is wrong (should be `timer: true` per CLAUDE.md rule D4: "timer: true ONLY on passive states") or the spec intentionally hides timers on multi-hour cold rests. Flag for D4 audit (see Draft 4).
- **`ny-style-pizza.json:COLD_PROOF` (2880 min, `timer: false`)** — same pattern, 48-hour cold proof. Likely same root cause.
- **Stretch & fold states with `timer: true`** (`stretch-fold-2/3/4` in jalapeño sourdough, 30 min each). The 30 min covers ~5 min of action (the fold) plus 25 min of rest. Currently classified as `passive_proof` — technically the baker does 5 min of work mid-window. Acceptable approximation; the absolute error per recipe is ≤15 min and the scheduler only cares about "is the baker free during this block" at a coarse grain.
- **`atk-cinnamon-buns-ultimate.json:BAKE` (37 min, stage `BAKE`)** — classifier worked correctly after the case-insensitive fix, but earlier draft classified this as `passive_proof` because the stage-id match was case-sensitive. Lesson: backfill script must lowercase stage IDs before matching.
- **`sourdough-cheddar-bay-biscuits.json:PREP_WORKSPACE` (5 min)** — title is "Preheat & Gather" and includes turning the oven on, but the state's primary action is gathering tools. Classifier mistakenly counted 5 min toward `oven_occupancy_min` because of the word "preheat" in the title. Backfill script needs a stricter preheat predicate (require `id` to literally start with `preheat`, or split the state in the JSON).
