## Spike goal

Decide whether PF-182 (replace baking cadence with contribution calendar) should:
1. Pull in `vue3-calendar-heatmap` (razorness) and style/extend it, OR
2. Build a from-scratch Vue 3 SVG component

And separately decide:
3. Whether to introduce a precomputed `public/recipes/bake-index.json` (date → bake count + recipe refs) vs keep deriving calendar data at runtime from recipe JSONs (current approach in `StatsPage.vue:105-244`).

## Background

- GitHub's own contribution graph is **proprietary** (not open-sourced)
- `vue3-calendar-heatmap` is the closest Vue 3 / TypeScript option, SVG-based, accepts `{date, count}` data
- Default tooltip is text-only via Tippy.js — **does not support rich HTML popovers with hero thumbnails**
- PF-182 requires the existing `TimelineBakeInfo` popover (recipe name + hero thumbnail + click → bake detail), which is already implemented in `StatsPage.vue` (lines 491-591)
- From-scratch is estimated ~100-200 lines of Vue SVG

## What to prototype

### Option A: Library + custom popover overlay
1. `npm install vue3-calendar-heatmap` (don't commit, this is a throwaway spike)
2. Wire it into a throwaway page (e.g., `DemoCalendar.vue` under `src/components/`) with fake bake data
3. Attempt to intercept cell hovers to render the existing `StatsPage.vue` popover on top of the library's SVG
4. Assess: how hard is the overlay? Does the library's default styling (green gradient, rounded corners) fight our brand?

### Option B: From scratch
1. Build a minimal Vue SVG component (`ContributionCalendar.vue`) that takes `{date: 'YYYY-MM-DD', count: number, aberration: boolean}[]` and renders 7 rows × ~53 cols of 0-radius squares
2. Wire the existing popover pattern directly (reuse `showPopover`, `navigateToBake`, `Teleport to body`)
3. Assess: how much code, how clean does it look, does it match GitHub's layout math correctly?

### Option C: bake-index.json optimization (evaluate independently)
1. Count: how many recipe JSONs are currently fetched on `/stats` page mount?
2. Measure: how large is the combined JSON payload for calendar data only (date + bake count + recipe id + hero thumb)?
3. Sketch the shape of `public/recipes/bake-index.json`: `[{ date, recipes: [{ id, name, heroThumb, aberration }] }]`
4. Assess: is the payload reduction + load speedup worth the build-time index generation step, or is runtime derivation fine at current scale?

## Deliverable
