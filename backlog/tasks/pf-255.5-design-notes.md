## 1. TypeScript Interface — `PricingProfile`

Add to `src/types/pricing.ts` (new file — keeps pricing concerns out of `recipe.ts`, which is already 850 lines and recipe-data-shaped).

```ts
/**
 * Recipe identifier — string matching `RecipeEntry.id` from
 * `public/recipes/index.json`. Aliased here for self-documentation;
 * the codebase does not define a global `RecipeId` type and passes
 * recipe ids as bare strings (see useScratchpad.ts, useProgress.ts).
 */
export type RecipeId = string

/**
 * Per-recipe pricing overrides. All fields optional — absent fields
 * fall back to `PricingProfile.default` (see resolveMarkupPct).
 */
export interface PricingProfileRecipeOverride {
  /** Markup percentage applied to ingredient cost. 0–500. */
  markupPct?: number
  /**
   * Hard sell-price override in dollars. When present, this takes
   * precedence over computed (cost × markup) AND the pretty-price snap
   * from PF-255.2 — i.e. the user has manually locked this price.
   * Display layer should badge the row as "manual" when sellPrice is set.
   */
  sellPrice?: number
  /** Free-form user note (e.g. "matches Goodall's $9 retail"). */
  notes?: string
}

/**
 * Profile-wide defaults. Lives at the top level so future fields
 * (laborRate, overheadPerBake) can live alongside markupPct without
 * widening every per-recipe override row.
 */
export interface PricingProfileDefaults {
  /** Default markup percentage used when a recipe has no override. */
  markupPct: number
  // Reserved for future expansion — keep additive only, never remove:
  // laborRatePerHour?: number   // PF-255.3 throughput modeling
  // overheadPerBake?: number    // fixed cost per bake (utilities, etc.)
  // currency?: 'USD' | 'EUR'    // currently USD-only; add when needed
}

/**
 * Top-level pricing profile. Serialized to JSON for export/import and
 * for the committed default at `public/profiles/pricing/default.json`.
 */
export interface PricingProfile {
  /**
   * Display name. Used to derive the slugified filename on export.
   * Examples: "Default", "Holiday 2026", "Farmers Market".
   */
  name: string
  /**
   * Profile schema version (semver). Independent of recipe versions.
   * Bump major when a breaking schema change happens (e.g. removing a
   * field). Importers reject mismatched majors; minor/patch are accepted.
   */
  version: string
  /** ISO 8601 date of profile creation. Set once, never auto-mutated. */
  created: string
  /** ISO 8601 date of last save/export. Updated on every write. */
  updated: string
  /** Profile-wide defaults — fallback when perRecipe entry is absent. */
  default: PricingProfileDefaults
  /**
   * Per-recipe overrides. Keys are recipe ids. Entries omitted from this
   * map fall through to `default`. Absent fields within an entry also
   * fall through — see resolveMarkupPct.
   */
  perRecipe: Record<RecipeId, PricingProfileRecipeOverride>
}
```

### Field rationale (per request)

- **`name`** — required, drives filename slug; user can fork ("Holiday Pricing", "Wholesale").
- **`version`** — semver string. Lets future imports reject incompatible schemas. Initial value: `"1.0.0"`.
- **`created` / `updated`** — both ISO date strings. `created` is forensic ("when did I start this profile?"); `updated` drives the staleness badge on the import-history surface (future).
- **`default.markupPct`** — required (non-optional) because hierarchy resolution needs a guaranteed fallback before the hardcoded constant. If a user wipes their default in the UI, the system enforces a minimum of 0 and the hardcoded constant only kicks in for malformed/legacy data.
- **`default` as a nested object** (not a flat `defaultMarkupPct: number`) — leaves headroom for PF-255.3 (`laborRatePerHour`) and future cost knobs without flattening migration. JSON nesting is cheap; schema evolution isn't.
- **`perRecipe[id].markupPct?`** — optional so the dirty-state diff is meaningful: "no override" is a distinct state from "override = same as default".
- **`perRecipe[id].sellPrice?`** — hard manual lock. Distinct from markupPct because the user may want to lock a retail price independent of fluctuating ingredient cost (e.g. "always sell at $12, even if cost drops").
- **`perRecipe[id].notes?`** — free-form. Doesn't drive math; surfaces as a tooltip on the row. Cheap to add, expensive to retrofit.
- **No `perRecipe[id].updated`** — the profile-level `updated` is sufficient. Per-row timestamps add storage cost with no UI use case in slice 1.

### Initial seed (for `public/profiles/pricing/default.json`)

```json
{
  "name": "Default",
  "version": "1.0.0",
  "created": "2026-05-12",
  "updated": "2026-05-12",
  "default": { "markupPct": 65 },
  "perRecipe": {}
}
```

## 2. Storage Path Convention

### On-disk (committed, served via Vite static):

```
public/profiles/pricing/
├── default.json                # baseline profile, version-controlled
├── holiday-2026.json           # additional named profiles (optional)
└── farmers-market.json
```

- Path: `public/profiles/pricing/<slug>.json`
- **Slug rules** (apply when deriving filename from `profile.name`):
  - Lowercase
  - Replace whitespace and underscores with single hyphen
  - Strip everything that is not `[a-z0-9-]`
  - Collapse repeated hyphens; trim leading/trailing hyphens
  - Examples:
    - `"Default"` → `default`
    - `"Holiday 2026"` → `holiday-2026`
    - `"Farmers' Market!!"` → `farmers-market`
- **Default profile is reserved**: a profile named "Default" always slugs to `default` and is the one auto-loaded on first visit. The implementer should expose `default.json` via the dev/prod static server with no auth.
- **Mkdir on first export**: if `public/profiles/pricing/` doesn't exist when the user authors the first JSON, they create it manually during commit. The /pricing UI itself never writes to disk — it only triggers downloads.

### In-browser (working state):

- **localStorage key:** `pricing-profile-current`
- **Value:** stringified `PricingProfile` JSON
- One active profile at a time in slice 1. Profile switching is out of scope for PF-255.1 (note this in implementer-facing readme).
- Additional bookkeeping key: `pricing-profile-committed-hash` — SHA-1 (or simple JSON.stringify hash) of the last-imported committed JSON, used for dirty-state diff. See §4.

## 3. Export / Import Flow

### Export

**Trigger:** "Export profile JSON" button on `/pricing` page (top-right of the page header per PF-255.1 #6).

**Behavior:**

1. Read `pricing-profile-current` from localStorage; parse to `PricingProfile`.
2. Bump `updated` field to today's ISO date (`YYYY-MM-DD`).
3. Persist the updated profile back to localStorage (so the export-time bump is reflected in working state too).
4. Slug the profile name (§2 rules) — call this `slug`.
5. Build the filename: `pricing-profile-<slug>-<YYYY-MM-DD>.json` (date is `updated`).
6. Stringify with `JSON.stringify(profile, null, 2)` for human-readable diffs in git.
7. Trigger a browser download via `Blob` + temporary anchor:

```ts
function exportProfile(profile: PricingProfile) {
  const updated = { ...profile, updated: new Date().toISOString().slice(0, 10) }
  localStorage.setItem('pricing-profile-current', JSON.stringify(updated))
  const blob = new Blob([JSON.stringify(updated, null, 2)], { type: 'application/json' })
  const url = URL.createObjectURL(blob)
  const a = document.createElement('a')
  a.href = url
  a.download = `pricing-profile-${slugify(updated.name)}-${updated.updated}.json`
  document.body.appendChild(a)
  a.click()
  a.remove()
  URL.revokeObjectURL(url)
}
```

8. After export, clear the dirty-state badges by recomputing `pricing-profile-committed-hash` from the exported JSON. Rationale: the user has just "committed" their changes to a file they will manually drop into `public/profiles/pricing/`. Treat export-time state as the new baseline.

### Import

**Trigger:** "Import profile JSON" button next to Export. Opens a hidden `<input type="file" accept="application/json">`.

**Behavior:**

1. Read the selected file as text.
2. `JSON.parse` — on failure, show inline error: "Not valid JSON".
3. **Validate** against schema (see Validator recommendation below). On failure, show field-level errors and abort.
4. Reject if `version` major does not match the app's current major (`1.x.x`). Show: "Profile schema vX.Y.Z is incompatible (expected 1.x)."
5. On success: write to `pricing-profile-current` localStorage; recompute and store `pricing-profile-committed-hash`; refresh the page state.

### Validator recommendation

**Recommend: manual TypeScript-guarded validator, not zod.**

Reasoning:

- The codebase currently has zero runtime validation libraries — adding zod is a 12 KB dependency for one feature surface.
- The profile schema is shallow (3 levels deep, ~6 fields total). A hand-written validator is ~30 lines and self-documents.
- Other parts of the codebase (`useRecipe.ts`, `useScratchpad.ts`) parse JSON without runtime validation; this pattern is established.

Sketch:

```ts
function validateProfile(raw: unknown): PricingProfile | { error: string } {
  if (typeof raw !== 'object' || raw === null) return { error: 'not an object' }
  const p = raw as Record<string, unknown>
  if (typeof p.name !== 'string' || !p.name) return { error: 'name missing' }
  if (typeof p.version !== 'string') return { error: 'version missing' }
  if (typeof p.created !== 'string') return { error: 'created missing' }
  if (typeof p.updated !== 'string') return { error: 'updated missing' }
  if (typeof p.default !== 'object' || p.default === null) return { error: 'default missing' }
  const d = p.default as Record<string, unknown>
  if (typeof d.markupPct !== 'number') return { error: 'default.markupPct missing' }
  if (typeof p.perRecipe !== 'object' || p.perRecipe === null) return { error: 'perRecipe missing' }
  // perRecipe entries: shallow check, ignore unknown keys forward-compat
  for (const [id, entry] of Object.entries(p.perRecipe)) {
    if (typeof entry !== 'object' || entry === null) return { error: `perRecipe[${id}] invalid` }
    const e = entry as Record<string, unknown>
    if (e.markupPct !== undefined && typeof e.markupPct !== 'number') return { error: `perRecipe[${id}].markupPct must be number` }
    if (e.sellPrice !== undefined && typeof e.sellPrice !== 'number') return { error: `perRecipe[${id}].sellPrice must be number` }
    if (e.notes !== undefined && typeof e.notes !== 'string') return { error: `perRecipe[${id}].notes must be string` }
  }
  return raw as PricingProfile
}
```

### First-load behavior

On `/pricing` mount:

1. Read `pricing-profile-current` from localStorage.
2. If present → parse, validate, use as working state.
3. If absent → `fetch('/profiles/pricing/default.json')`:
   - On 200: parse, validate, write to localStorage, store hash as `pricing-profile-committed-hash`.
   - On 404 or fetch error: seed an empty profile with `default.markupPct = 65` and `perRecipe = {}`; store both localStorage values immediately so future loads are deterministic.
4. If validation fails on the fetched committed profile, log a console warning and seed empty — never crash the page.

## 4. Dirty-State Diff UI Spec

### Trigger condition

A per-recipe row is **dirty** when the user's localStorage `PricingProfile.perRecipe[id]` (or the absence thereof) differs from the corresponding entry in the last-imported committed profile.

**Diff granularity:** entire entry, not per-field. If `localStorage.perRecipe[id]` deep-equals `committed.perRecipe[id]` (treating `undefined` and missing key as equivalent), row is clean. Otherwise dirty.

The profile-level fields (`name`, `default.markupPct`, etc.) get their own dirty badge on the page header (not per-row).

### Where "committed" lives

The implementer stores the last-imported (or first-fetched-from-default.json) profile under a second localStorage key: `pricing-profile-committed`. This is the baseline for diffing. It's updated only:

- On successful **import**
- On successful **export** (export resets the baseline — the user has "committed" by downloading)
- On first load when `default.json` is fetched

Never updated by user edits in the UI. That is the entire point of the dirty-state surface.

### Visual spec

- **Badge text:** `modified` (lowercase, monospace, matches `proofed.` brand tone)
- **Badge color:** accent (`#a65d45`, same red dot color as brand); text `bg-accent text-white` per existing UnoCSS tokens
- **Shape:** small pill, 2px solid border (matches B4 sharp-edge rule from CLAUDE.md), padding `px-1.5 py-0.5`, font-size 10–11px
- **Position:** inline at the end of the recipe name within each row, right after the name and before the cost column. Not in a separate column — saves horizontal space on mobile.
- **Hover/tap tooltip (desktop only):** "Differs from committed default. Export to save."
- **Page-header dirty badge** (when `default.markupPct` or profile metadata is dirty): same styling, appears next to the profile name in the page header.

### Computation strategy

**Per render via `computed`.** Not a watcher. Rationale:

- `pricing-profile-current` is already reactive (held in a `ref` or `reactive` after parsing).
- `pricing-profile-committed` is loaded once on mount, then mutated only on import/export — already a stable reactive ref.
- A `computed(() => deepEqual(current.perRecipe[id], committed.perRecipe[id]))` per row is O(1) on entry size (≤3 fields). With ~50 recipes that's 50 cheap computations, well under any perf threshold.
- A watcher would have to fire on every slider tick and maintain its own dirty map — strictly more code with no benefit.

Implement `deepEqual` as a small helper that treats `undefined` and missing keys as equal, ignores `notes` whitespace only if both sides are non-empty (or just keeps it strict — the simpler path).

### What clears dirty state

| Action | Effect |
|---|---|
| Export profile JSON | Resets `pricing-profile-committed` to current; all rows clean |
| Import profile JSON | Replaces `pricing-profile-committed` with imported; rows clean unless user has unsaved local edits beyond the imported file |
| Manual revert button on row (optional, slice 1.5) | Restores that row's localStorage entry to match committed; row clears |
| User edits a value back to match committed | Row clears automatically (because `computed` recomputes) |
| User edits any value away from committed | Row goes dirty automatically |

**No auto-clear on page reload.** Dirty-state persists across sessions until the user exports or imports.

## 5. Hierarchy Resolution Rule

### Function signature

```ts
import type { PricingProfile, RecipeId } from '@/types/pricing'

/**
 * Resolve the markup percentage to apply to a recipe.
 * Three-tier cascade:
 *   1. Profile's per-recipe override (perRecipe[id].markupPct)
 *   2. Profile-wide default (default.markupPct)
 *   3. Hardcoded fallback constant (FALLBACK_MARKUP_PCT = 65)
 * Returns a number in [0, ...]. Caller is responsible for clamping if a
 * UI bound is needed.
 */
export const FALLBACK_MARKUP_PCT = 65

export function resolveMarkupPct(
  recipeId: RecipeId,
  profile: PricingProfile
): number {
  const override = profile.perRecipe[recipeId]?.markupPct
  if (typeof override === 'number' && Number.isFinite(override)) {
    return override
  }
  if (typeof profile.default.markupPct === 'number' && Number.isFinite(profile.default.markupPct)) {
    return profile.default.markupPct
  }
  return FALLBACK_MARKUP_PCT
}
```

### Tier rationale

1. **Per-recipe override** — most specific, always wins when present. `undefined` (field absent) and `null` both fall through, but `0` is a valid intentional value and must NOT fall through. This is why we type-check with `typeof === 'number'` and reject `null`/`undefined` only.

2. **Profile default** — the profile-wide fallback. Required field in the schema (non-optional), so this tier should always exist in well-formed profiles. The defensive `Number.isFinite` check protects against malformed imports.

3. **Hardcoded `FALLBACK_MARKUP_PCT = 65`** — final safety net. 65% chosen as a reasonable food-business gross margin floor; matches the seed value in the default profile. The constant lives in the pricing types module (or a sibling `src/lib/pricing.ts`) and is exported so tests can reference it.

### Sell-price resolution (related)

When a row has `perRecipe[id].sellPrice` set, it bypasses the markup cascade entirely. Resolution order for the displayed sell price:

```ts
export function resolveSellPrice(
  recipeId: RecipeId,
  ingredientCost: number,
  profile: PricingProfile,
  prettySnap: (raw: number) => number  // from PF-255.2
): { price: number; source: 'manual' | 'computed' } {
  const manual = profile.perRecipe[recipeId]?.sellPrice
  if (typeof manual === 'number' && Number.isFinite(manual)) {
    return { price: manual, source: 'manual' }
  }
  const markup = resolveMarkupPct(recipeId, profile)
  const raw = ingredientCost * (1 + markup / 100)
  return { price: prettySnap(raw), source: 'computed' }
}
```

The `source` field lets the UI badge manual prices distinctly from computed/snapped prices.

## 7. Out of Scope (deferred)

- Profile switching UI (multiple named profiles in one session)
- Server-side persistence (profiles are user-local in slice 1)
- Per-recipe `updated` timestamps
- Currency other than USD
- Auto-export on every edit (intentional friction — user signals "save" by clicking Export)
- Conflict resolution on import when local edits exist (current rule: import wipes local working state; future: prompt user)
