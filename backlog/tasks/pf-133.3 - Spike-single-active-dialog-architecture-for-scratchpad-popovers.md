## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Currently each ScratchpadNote popover manages its own isOpen state independently. Multiple popovers could be open simultaneously. Need shared state so only one dialog is active at a time — opening one closes the others (including the GeneralNotesFab panel).

**Options to explore:**
- Shared reactive `activePopoverId` in the scratchpad composable
- Event bus approach (close-all event when any opens)
- Provide/inject from a parent wrapper

Should also consider interaction with TOC sidebar and other overlays.

## AC2: Three Approaches Evaluated

### Approach A: Shared Reactive `activeDialogId` in useScratchpad Composable

**How it works**: Add a `ref<string | null>` to the module-level state in `useScratchpad.ts`. When any overlay opens, it sets `activeDialogId` to its unique ID. All participants watch this ref and close themselves when it changes to something other than their ID.

**Pros**:
- Natural home — scratchpad composable already manages shared module-level state (`const state = reactive<ScratchpadState>(...)`)
- Zero prop drilling for ScratchpadNote — it already receives the composable return value as a prop, just add `activeDialogId` + `requestOpen(id)` to the return
- GeneralNotesFab already receives scratchpad data from App.vue — one more method/ref is trivial
- Esc key: each component handles its own Esc, just calls `clearActiveDialog()` which sets ID to null
- Single source of truth for "what's open" — easy to debug

**Cons**:
- Couples non-scratchpad overlays (GeneralNotesFab, TocSidebar mobile) to the scratchpad composable — conceptual smell
- File change count: 3-4 files (useScratchpad.ts, ScratchpadNote.vue, GeneralNotesFab.vue, optionally TocSidebar.vue)
- The composable is recipe-scoped (takes `recipeId`), but dialog state is page-scoped — minor mismatch

**Variant A2: Separate `useActiveDialog` composable**
Extract the `activeDialogId` into its own composable (`useActiveDialog.ts`) with module-level state. Any component imports it directly — no prop drilling at all, since module-level reactives are singletons.

**Pros of A2 over A**: Clean separation of concerns; any overlay can participate without depending on scratchpad
**Cons of A2 over A**: One more file, but very small (~20 lines)

### Approach B: Event Bus (mitt or native CustomEvent)

**How it works**: When any overlay opens, it dispatches a `dialog:open` event with its ID. All other participants listen for this event and close themselves if they're open. Could use `mitt` (tiny pub/sub lib) or native `CustomEvent` on `window`.

**Pros**:
- Zero coupling between components — fully decoupled
- No prop drilling at all
- Works at any tree depth
- Easy to add new participants

**Cons**:
- Hard to trace/debug — event flow is invisible in Vue DevTools
- Cleanup burden — every component must `addEventListener`/`removeEventListener` (or `mitt.on`/`mitt.off`)
- Race conditions possible if events fire during transitions
- Non-reactive — can't `watch()` or `computed()` the current active dialog
- Adds a dependency (mitt) or relies on DOM events (less Vue-idiomatic)
- File change count: 4-5 files (bus setup, ScratchpadNote, GeneralNotesFab, TocSidebar, + possibly a cleanup composable)
- No single source of truth for "what is currently open" — each component tracks its own state

### Approach C: Provide/Inject from Parent Wrapper

**How it works**: A parent component (App.vue or a new wrapper) provides a reactive `activeDialogId` ref via `provide()`. Children use `inject()` to read/write it.

**Pros**:
- Vue-idiomatic for parent-child state sharing
- Reactive — can `watch()` or use in `computed()`
- No event bus dependency

**Cons**:
- **Critical problem**: ScratchpadNote is 3 levels deep (App → StageCard → StateStep → ScratchpadNote). Provide/inject works across depth, so this is actually fine.
- But: provide/inject is designed for "ancestor provides, descendant consumes." It works well here.
- Requires App.vue to set up the provider — ties it to the component tree
- File change count: 3-4 files (App.vue for provide, ScratchpadNote for inject, GeneralNotesFab for inject)
- Testing is harder — must wrap test components with a provider

## AC3: Recommendation

**Recommended: Approach A2 — Separate `useActiveDialog` composable with module-level singleton state.**

**Rationale**:

1. **Minimal prop drilling**: Zero. Module-level `ref` means any component can `import { useActiveDialog } from '@/composables/useActiveDialog'` and get the same reactive state. No props, no provide, no inject.

2. **Composable pattern compatibility**: This project already uses the module-level singleton pattern in `useScratchpad.ts` (line 10: `const state = reactive<ScratchpadState>({...})`). The `useActiveDialog` composable follows the exact same pattern — a module-level ref that all callers share.

3. **Deep component tree access**: ScratchpadNote at depth 3 (App → StageCard → StateStep → ScratchpadNote) can import the composable directly. No need to thread a prop through StageCard and StateStep.

4. **Esc key interaction**: Each component calls `useActiveDialog().close()` on Esc, which sets `activeId` to `null`. Other components reactively detect this via `watch()` or computed and close their own UI. Clean, traceable.

5. **Separation of concerns**: Dialog coordination is independent from scratchpad data. The `useActiveDialog` composable knows nothing about notes, ratings, or recipes. It just tracks "which overlay is active."

6. **Testability**: Module-level state can be reset between tests. No provider wrappers needed.

7. **File change count**: Minimal — 1 new file (~20 lines), 2-3 modified files (ScratchpadNote.vue, GeneralNotesFab.vue, optionally TocSidebar.vue for mobile sheet).

## AC4: Participation Boundary

### PARTICIPATES in single-active coordination:

**ScratchpadNote** — YES
- Primary problem case. Multiple instances (10-20+ per page) each with independent `isOpen`. Opening one should close all others + GeneralNotesFab.
- z-30 popovers would visually stack if multiple open.

**GeneralNotesFab** — YES
- Conceptually related to scratchpad notes. Both are "note-taking overlays." Having the FAB panel open while a step popover is also open is confusing.
- Both compete for user attention in the same workflow (capturing bake notes).

### INDEPENDENT — does NOT participate:

**TocSidebar desktop** — NO (not a dialog)
- Always-visible sticky sidebar. Not an overlay. No open/close state.
- No conflict possible.

**TocSidebar mobile bottom sheet** — NO
- Different spatial zone (bottom-right FAB) vs scratchpad (bottom-left FAB + inline popovers).
- Different purpose: navigation vs data capture. User might want TOC open while jotting a note.
- z-50 with backdrop already creates its own modal context.
- If we included it, opening a ScratchpadNote (z-30, no backdrop) would dismiss the TOC sheet (z-50, with backdrop) — weird UX inversion where a "lesser" overlay dismisses a "greater" one.

**PhotoLightbox** — NO
- Full-screen takeover at z-100. Locks body scroll.
- When lightbox is open, nothing else is interactable anyway.
- It already has its own Esc handler and backdrop click.
- Including it would mean opening a scratchpad note closes the lightbox — wrong behavior.

**ShareModal** — NO
- True modal with backdrop and scroll lock at z-50.
- Opened via exposed `open()` method from parent, not user-discoverable FAB.
- Same reasoning as PhotoLightbox — it creates its own isolated context.
- Including it would mean opening a scratchpad note closes the share modal — wrong behavior.

### Summary Table
```
Overlay              | Participates | Reason
---------------------|-------------|------------------------------------------
ScratchpadNote       | YES         | Primary problem; many instances, z-30
GeneralNotesFab      | YES         | Same workflow; conceptual sibling
TocSidebar desktop   | NO          | Not a dialog; always visible
TocSidebar mobile    | NO          | Different zone/purpose; higher z-layer
PhotoLightbox        | NO          | Full-screen takeover; isolated context
ShareModal           | NO          | True modal; isolated context
```

## AC5: Pseudocode for Recommended Approach

```typescript
// ============================================================
// src/composables/useActiveDialog.ts (NEW — ~25 lines)
// ============================================================
import { ref, readonly } from 'vue'

// Module-level singleton — shared across all callers
const activeId = ref<string | null>(null)

export function useActiveDialog() {
  /** Open a dialog by ID. Automatically closes any other active dialog. */
  function open(id: string): void {
    activeId.value = id
  }

  /** Close the currently active dialog (or a specific one). */
  function close(id?: string): void {
    // If id provided, only close if it matches (prevents stale closes)
    if (id && activeId.value !== id) return
    activeId.value = null
  }

  /** Check if a specific dialog is currently active */
  function isActive(id: string): boolean {
    return activeId.value === id
  }

  return {
    activeId: readonly(activeId),
    open,
    close,
    isActive,
  }
}
```

## Bonus Findings

### Missing Esc Handlers
During inventory, found that **GeneralNotesFab** and **TocSidebar mobile sheet** have no Esc key handlers. This is a separate bug/improvement but worth noting. The `useActiveDialog` implementation provides a natural place to add Esc handling for GeneralNotesFab.

### Click-Outside for ScratchpadNote
ScratchpadNote has no backdrop and no click-outside detection. With single-active-dialog, this becomes less important (opening anything else closes it), but a `@click.outside` directive or `onClickOutside` composable from VueUse could be a nice addition later.

### Transition Timing
The `v-if="isOpen"` with `<Transition>` will work naturally with the computed approach. Vue transitions fire on `v-if` changes regardless of whether the value comes from a `ref` or `computed`. No changes needed to transition animations.
