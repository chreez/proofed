## 1. Contribution Profit (CP) — Formula

### Canonical accounting definition

Contribution margin (a.k.a. contribution profit / CP in this project) is the amount left from each unit's sale price after subtracting variable cost per unit. It is the per-unit money that "contributes" to fixed costs and profit.

Two forms — dollar (per unit) and ratio (percent of sell price):

```
CP_per_unit  = sellPrice - variableCostPerUnit          // $ per item
CP_ratio     = CP_per_unit / sellPrice                  // 0..1 (multiply ×100 for %)
```

Variable cost per unit, for a retail bakery item, is the sum of ingredient cost (gram-weighted) + per-unit packaging + any per-unit consumables (parchment, sticker, bag). Labor and overhead (rent, utilities, equipment depreciation) are **fixed** — they do not enter CP.

TS-ready pseudocode:

```ts
type PricingInputs = {
  sellPrice: number;        // $ per unit
  variableCost: number;     // $ per unit (ingredients + packaging + per-unit consumables)
};

function contributionProfit(p: PricingInputs) {
  const cp = p.sellPrice - p.variableCost;
  const cpPct = p.sellPrice > 0 ? cp / p.sellPrice : 0;
  return { cp, cpPct };
}
```

   https://verifiedmetrics.com/blog/unit-contribution-margin-formula

### Project-specific notes / assumptions

- **Naming:** product calls this CP ("contribution profit"). Accounting literature uses CM ("contribution margin"). Same thing — keep CP in UI copy for brand fit, but internal docs can use either.
- **Variable cost scope (ASSUMPTION):** for slice 1, `variableCost` = the recipe's resolved ingredient cost (already produced by `/cost` skill, lives in `cook_log[].cost.items[]`) + any per-unit packaging entry. Labor stays fixed/out for v1; revisit when scheduler lands (PF-255.3+).
- **Markup vs CP relationship:** `sellPrice = cost × (1 + markupPct/100)` implies
  `CP% = markupPct / (100 + markupPct)`. E.g., 150% markup → 60% CP. Useful for UI sanity check.

## 2. Psych-pricing breakpoint research

### Prevalence data (1997 retail study, still the canonical citation)

| Ending | Share of retail prices |
|--------|------------------------|
| 9      | ~60.7%                 |
| 5      | ~28.6%                 |
| 0      | ~7.5%                  |
| other  | ~3%                    |

(Source: Marketing Bulletin study cited by Wikipedia's psychological pricing entry.)

### When each ending wins

- **$X.99** — dominant for everyday / impulse / value-priced retail. The "left-digit effect" makes $2.99 read as "$2-something" rather than "$3". Strongest lift when the leftmost digit changes ($2.99 → $3.00 matters; $22.99 → $23.00 less so).
- **$X.95** — softer charm pricing. Common in food retail, craft bakeries, farmers-market goods. Less aggressive than .99; reads as "tidy" while still beating the round.
- **$X.50** — middle-ground breakpoint, common for items priced in dollars (esp. $5-$15 baked goods). Works when the seller wants to look fair/honest without going full-charm.
- **Whole dollar ($X.00)** — prestige / premium / artisan framing. High-end retailers and restaurants often round up. Signals confidence and quality; appropriate for specialty items where price is part of the value cue.

### Range guidance (synthesis — partly inferred, see assumptions)

| Price range | Recommended breakpoints (in order of preference) |
|-------------|--------------------------------------------------|
| < $5        | $X.99, $X.95, $X.50                              |
| $5 – $10    | $X.99, $X.95, $X.50, $X.00                       |
| $10 – $20   | $X.99, $X.50, $X.00 (whole dollar starts to compete) |
| $20 – $30   | $X.00, $X.99, $X.50 (whole dollar for premium framing) |

**Assumption:** above table is a synthesis of the cited sources — no single source publishes a clean range-by-range table for bakery items specifically. Confidence: high on the .99 dominance and on the premium-rounding pattern at higher prices; medium on exact tier cutoffs.

## 3. Snap algorithm — pseudocode

### Inputs / outputs

```ts
type SnapInputs = {
  cost: number;        // variable cost per unit ($)
  markupPct: number;   // e.g., 150 means +150%
};

type SnapResult = {
  rawPrice: number;        // unsnapped target
  prettyPrice: number;     // snapped to nearest allowed breakpoint
  nextPrettyUp: number;    // next higher pretty value
  nextPrettyDown: number;  // next lower pretty value
  profitAtPretty: number;  // CP at prettyPrice
  profitAtNextUp: number;  // CP at nextPrettyUp
  profitAtNextDown: number;// CP at nextPrettyDown
};
```

### Breakpoint policy (by price range)

```ts
// Returns the set of allowed cent-endings for a given dollar amount.
// Higher in the list = preferred when distances tie.
function allowedEndings(price: number): number[] {
  // endings expressed as cents: 99, 95, 50, 00
  if (price < 5)   return [99, 95, 50];
  if (price < 10)  return [99, 95, 50, 0];
  if (price < 20)  return [99, 50, 0];
  return [0, 99, 50]; // >= $20 → prefer whole dollar
}
```

### Core snap algorithm (pseudocode)

```
function snap(cost, markupPct):
    rawPrice = cost * (1 + markupPct / 100)

    candidates = generateCandidates(rawPrice)
        // For the integer dollar floor D = floor(rawPrice):
        //   for each ending in allowedEndings(rawPrice):
        //     candidate = D + ending/100
        //     if candidate < rawPrice - $1, skip (too far below)
        //   Also produce D+1+ending/100 for endings 0, 50, 95, 99
        //   so we have both a "down" and "up" candidate set.

    sortedByDistance = candidates.sort((a, b) => |a - rawPrice| - |b - rawPrice|)

    prettyPrice    = sortedByDistance[0]
    nextPrettyUp   = smallest candidate > prettyPrice
    nextPrettyDown = largest candidate < prettyPrice

    return {
        rawPrice,
        prettyPrice,
        nextPrettyUp,
        nextPrettyDown,
        profitAtPretty:     prettyPrice    - cost,
        profitAtNextUp:     nextPrettyUp   - cost,
        profitAtNextDown:   nextPrettyDown - cost,
    }
```

### Worked examples (sanity check, manual)

| cost | markup% | raw  | range tier | allowed endings | snapped | up    | down  |
|------|---------|------|------------|-----------------|---------|-------|-------|
| 1.20 | 200     | 3.60 | <$5        | 99, 95, 50      | 3.50    | 3.95  | 2.99  |
| 2.80 | 150     | 7.00 | $5-$10     | 99, 95, 50, 00  | 6.99    | 7.50  | 6.50  |
| 4.50 | 180     | 12.60| $10-$20    | 99, 50, 0       | 12.50   | 12.99 | 12.00 |
| 9.00 | 180     | 25.20| ≥$20       | 0, 99, 50       | 25.00   | 25.50 | 24.99 |

(All four pass eyeball test; "snapped" is whichever candidate has min |Δ| from raw, with preference order breaking ties.)

### Edge cases & guardrails (CALL OUTS for slice 1 implementation)

- **Floor at cost:** never snap below `cost` itself (would render negative CP).
  If the nearest pretty < cost, fall back to the nearest pretty ≥ cost and surface a warning.
- **Tiny prices (< $1):** out of scope for v1. ASSUMPTION: bakery items are $3+. If hit, fall back to nearest 5-cent increment.
- **Tie-breaking:** when two candidates are equidistant, use `allowedEndings()` order (first-listed wins).
- **Range boundary:** `rawPrice` of $9.95 falls in <$10 tier, $10.00 falls in $10-$20 tier. The snap uses `rawPrice`'s tier, not the candidate's — so a $9.95 raw can snap up to $10.00 (cross-tier) cleanly because $10.00 is in the candidate set for the rawPrice tier (ending 0 is allowed in $5-$10).

## 4. Bulk-amortization formula (for later slice — capture only)

Use case: user buys flour in 25kg sacks at $40 ($1.60/kg = $0.0016/g). Recipe uses 500g. Cost of flour attributable to one bake = `500 × 0.0016 = $0.80`.

This is the simple per-gram method (see Station Bakery source). It implicitly amortizes the bulk purchase across all future uses at the moment of purchase: cost-per-gram is fixed for the life of the sack, and each bake "draws down" proportional value.

### Formulas

```
costPerGram   = bulkPrice / bulkGrams
recipeFlourCost = recipeFlourGrams × costPerGram
```

**Break-even uses of a bulk purchase** (how many bakes until the bulk-vs-retail savings pays back the upfront outlay difference):

```
savingsPerBake = (retailPricePerGram - bulkPricePerGram) × gramsUsedPerBake
breakEvenBakes  = (bulkBagPrice - retailEquivalentPrice) / savingsPerBake
```

Worked example: 25kg bulk flour $40 ($0.0016/g) vs 5lb retail $4 (~$0.00176/g). Savings = ($0.00176 - $0.0016) × 500g = $0.08 per bake of 500g flour. To recoup buying the 25kg bag instead of incremental 5lb bags, it self-amortizes (lower upfront per-gram), so break-even is immediately on first use. The more relevant question is **shelf-life break-even**: will you use 25kg before spoilage? 25000g ÷ 500g per bake = 50 bakes. If shelf life of stored flour is ~6 months for AP, you need 50 bakes / 26 weeks ≈ 2 bakes/week to fully utilize.

### Source (accessed 2026-05-12)

1. **The Station Bakery — How to Calculate the Cost of Ingredients for a Home Bakery.**
   "Cost Per Unit = Total Cost ÷ Number of Units." Example: $3 / 2260g = ~$0.001/g.
   Confirms the per-gram approach. (Article does not address shelf-life amortization
   — that's an extension proposed here.)
   https://www.thestationbakery.com/blog/how-to-calculate-the-cost-of-ingredients-for-a-home-bakery

### Notes & assumptions

- **ASSUMPTION:** for slice 1, ignore bulk-amortization entirely — use whatever cost

  before PF-255 later slices (likely landed alongside scheduler / profile work).
- A more sophisticated model would account for spoilage probability, opportunity
  cost of capital tied up in bulk inventory, and storage space cost. Out of scope.
