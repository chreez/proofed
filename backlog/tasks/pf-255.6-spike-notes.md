# PF-255.6 Spike Notes: Recipe Metadata Audit for Pricing + Throughput

**Task:** Catalog gaps in existing recipe metadata that PF-255 pricing + throughput consumers need.

**Scope:** 26 recipe JSONs in `public/recipes/` (excluding `index.json`, `cost-rates.json`). Read-only audit — no recipe JSONs or source code modified.

**Field reference:** `src/types/recipe.ts` (canonical names verified).

---

## Executive Summary

- **26 recipes audited.**
- **Universal gaps (proposed PF-255.3 fields):** `meta.prep_active_min`, `meta.proof_passive_min`, `meta.oven_occupancy_min`, `meta.bake_min` — missing on all 26 recipes (do not exist in schema yet). Blocker for throughput modeling.
- **Strong baseline:** `meta.yields` and `meta.total_time` are present on every recipe (free-form strings).
- **Stats block (`config.stats`):** missing `defaultYield` + `servingsPerItem` on 6 recipes.
- **Nutrition:** missing entirely on 6 recipes (mostly unbaked recipes).
- **Cost data:** 14 recipes have no cook_log at all → no `cook_log[].cost`. Of the 12 with bakes, 5 have a cook_log entry whose most-recent `cost.items[]` is empty/absent; 1 (`ny-style-pizza`) is missing `cost.total` as well.

## 2. Backfill Plan

### A. Throughput time fields (proposed PF-255.3) — `prep_active_min`, `proof_passive_min`, `oven_occupancy_min`, `bake_min`

- **Affected:** 26 / 26 recipes (universal).
- **Schema status:** fields don't exist yet. Need a `RecipeMeta` extension in `src/types/recipe.ts` before backfill is possible. This is a hard dependency on PF-255.3 design landing first.
- **Seed strategy:**
  - `bake_min` — sum `duration_min` of states whose direction mentions "bake" or whose stage id contains "bake"; cross-check against parenthetical in `meta.total_time` (e.g., "20 min bake").
  - `oven_occupancy_min` — `bake_min` + preheat duration (look for state with `direction` containing "preheat" and `timer: true`).
  - `proof_passive_min` — sum `duration_min` of states with `timer: true` and stage id matching `bulk|proof|rise|retard|rest|ferment`.
  - `prep_active_min` — sum `duration_min` of states with `timer: false` (everything else hands-on). Sanity-check against the active-time figure already in `meta.total_time` strings (most recipes already record this parenthetically, e.g., "~5 hrs (1.5 active)").
- **Note:** seed values are estimates. The first bake's `bake_stats.bake_phases[]` (PF-177.3) will give actuals — backfill should NOT overwrite once real bake data exists for a phase.
- **Priority:** **Blocker** for PF-255.1 slice (throughput modeling). However, since the schema itself is being designed in PF-255.3, backfill should follow schema landing. Hold draft as "Backfill once PF-255.3 lands schema."

### B. `config.stats.defaultYield` + `config.stats.servingsPerItem`

- **Affected (6):** `ba-bolognese`, `jalapeno-cheddar-sourdough`, `sourdough-chocolate-chip-cookies`, `sourdough-discard-cheese-crackers`, `tartine-lemon-cream-tart`, `tartine-rugelach`.
- **Seed strategy:** parseable from existing `meta.yields` strings:
  - `ba-bolognese` → "4 servings" → `defaultYield: 4, servingsPerItem: 1, unit: "servings", servingUnit: "serving"`
  - `jalapeno-cheddar-sourdough` → "2 loaves (~730g each)" → `defaultYield: 2, servingsPerItem: 10` (match `nutrition.servings: 16`? mismatch — needs reconciliation; 16 / 2 loaves = 8 servings per loaf, but other sourdough loaves use 10). Flag for human review.
  - `sourdough-chocolate-chip-cookies` → "~22-24 cookies" + `nutrition.servings: 23` → `defaultYield: 23, servingsPerItem: 1`.
  - `sourdough-discard-cheese-crackers` → "~80-100 crackers (2 sheet pans)" → `defaultYield: 90, servingsPerItem: 1` (estimate).
  - `tartine-lemon-cream-tart` → "12 tartlets" + `nutrition.servings: 12` → `defaultYield: 12, servingsPerItem: 1`.
  - `tartine-rugelach` → "16 rugelach" → `defaultYield: 16, servingsPerItem: 1`.
- **Also need:** `unit` and `servingUnit` (per `RecipeStats` interface — not just the two numeric fields). Easy to derive from yields string.
- **Priority:** **Medium** — pricing slice (PF-255.1) needs `defaultYield` and `servingsPerItem` to compute per-unit and per-serving prices.

### C. Nutrition block

- **Affected (6):** `candida-focaccia`, `grain-free-bread`, `potato-buns`, `sourdough-discard-cheese-crackers`, `sourdough-pizza-dough`, `tartine-rugelach`.
- **Seed strategy:** run `/cost` or the existing nutrition calc skill against each. All 6 already have full `stages[].gather.ingredients[]` with gram amounts, so USDA FDC lookups should be straightforward. No new data needed.
- **Note:** all 6 are recipes with no cook_log yet (un-baked). Nutrition is a known D16 validation requirement (checklist), so backfill is already on the global to-do list — this audit just confirms which ones.
- **Priority:** **Medium** — pricing slice can render without nutrition, but per-serving cost vs. per-serving calorie comparison is a known PF-255 consumer.

### D. Cost data on recent cook_log entries

- **Affected (5 — bakes exist but most-recent cost.items[] is empty/absent):** `birote-salado`, `gochujang-garlic-buns`, `ny-style-pizza`, `simple-sourdough-wheat`, `sourdough-cinnamon-buns`.
- **Special case:** `ny-style-pizza` is missing both `cost.items[]` AND `cost.total` — entry has no cost data at all.
- **Seed strategy:** run `/cost` skill per recipe to populate `cost.items[]` from current HEB pricing + pantry rates. Note that some of these recipes have a `cost.total` only (legacy / aggregate-only entries) — `cost.items[]` line-items need to be rebuilt.
- **Priority:** **Medium** — pricing slice will fall back to `estimatedCost` block if cook_log cost data is sparse, so this is nice-to-have for PF-255.1 but valuable for cost-history charting.

### E. Cost data for un-baked recipes (14 recipes)

- **Affected (14):** `candida-focaccia`, `carrot-cake`, `coco-curry`, `grain-free-bread`, `ichiran-ramen`, `ny-pizza-sauce`, `potato-buns`, `sourdough-cheddar-bay-biscuits`, `sourdough-chocolate-chip-cookies`, `sourdough-discard-cheese-crackers`, `tartine-baguette`, `tartine-rugelach`, `thai-tea-boba`, `tomita-tsukemen`.
- **Seed strategy:** these recipes have never been baked, so `cook_log[].cost` is structurally absent. The right destination for pre-bake pricing is `Recipe.estimatedCost` (`EstimatedCost` interface in `recipe.ts`), not a cook_log entry. Spawn estimated-cost runs via `/cost` skill.
- **Priority:** **Low** — only matters once PF-255.1 starts wanting "what does this cost to bake?" on un-baked recipes. Defer until pricing UI is built.

### F. Nutrition / yield mismatches for human review

- `jalapeno-cheddar-sourdough` → `nutrition.servings: 16` but yields "2 loaves (~730g each)". Need to decide: is a serving 1/8 of a loaf or 1/10? Doesn't block PF-255, but the serving-to-yield ratio matters for per-serving pricing math.
- **Priority:** Low — flag for `/feedback` session, not a backlog task.

## 4. Open Questions for Orchestrator

1. **Schema ordering:** DRAFT-78 (throughput times) is hard-blocked on PF-255.3 landing the schema extension. Should this audit recommend bundling the schema change as part of DRAFT-78, or wait for PF-255.3 design first?
2. **`stats` block on non-yield recipes:** the 6 recipes missing stats are mostly batch-style (cookies, crackers, rugelach, tart, bolognese, sourdough). Should `defaultYield: 1` + `servingsPerItem: nutrition.servings` be the canonical pattern for these, or do we need item-level yields (e.g., "23 cookies, 1 cookie per serving")?
3. **Cost data direction:** for un-baked recipes, is `estimatedCost` (recipe-level) the right surface, or should PF-255 pricing consume `cook_log[*].cost` exclusively and require at least one bake? The `EstimatedCost` interface exists but is rarely populated — confirm intent before DRAFT-82.
