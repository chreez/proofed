## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Scratchpad icons, FAB, and reminder banners currently show on every recipe page load. They should only appear after the user explicitly starts a bake session.

**Questions to explore:**
- What triggers "bake started"? (First checkbox? Explicit "Start Bake" button? Auto-detect from progress?)
- Where does the start bake CTA live? (Hero area? Sticky header? First stage?)
- What state changes when a bake is active vs browsing? (scratchpad visible, progress tracking active, timer behavior?)
- How does a bake session end? (Explicit "End Bake"? Auto after last step? Timeout?)
- Does bake session state persist across page reloads? (localStorage alongside scratchpad data)
- How does this interact with the existing progress composable?

**Context:** Right now the recipe page is both a reference view (browsing) and a bake view (active cooking). This spike explores making that distinction explicit so the UI can adapt — scratchpad, reminders, and capture tools only surface when you're actually baking.

## AC1: Start Bake Trigger Options

### Option A: Explicit "Start Bake" button
**Where it lives:** RecipeMeta.vue — next to the existing "Copy Recipe" and "Reset Bake" buttons in the header card. Natural spot since RecipeMeta already has `hasProgress` prop and `@reset` emit.

**Pros:**
- Clear intent signal — zero ambiguity about whether the user is browsing or baking
- Clean state boundary: `bakeActive = true` flips on, scratchpad initializes, UI elements appear
- Works well with the "Reset Bake" button pattern already in RecipeMeta (currently emits `reset` to clear progress)
- Can record `startedAt` timestamp for bake duration tracking
- Mobile-friendly: a single tap starts bake mode

**Cons:**
- Extra step before the user can start checking things off — friction
- Users might forget to click it and just start checking boxes, then wonder where the scratchpad is
- Need to decide what happens when there's already progress but no active session (stale state from yesterday)

**Impact on composables:**
- `useProgress`: No changes needed. Progress tracking works independently today — it saves/loads from `recipe-progress-{id}` regardless. Start Bake just gates the scratchpad UI, not progress itself.
- `useScratchpad`: The `load()` call in App.vue (line 104) would become conditional on `bakeActive`. Currently scratchpad loads unconditionally on recipe load.
- New `useBakeSession` composable (or fold into useProgress — see AC4).

### Option B: First checkbox (auto-detect from first gather item check)
**Where it lives:** Triggered by `toggleItem()` or `toggleState()` in `useProgress.ts` (lines 86-98). When the first item/state goes from unchecked → checked and no bake session exists, auto-create one.

**Pros:**
- Zero friction — the user just starts doing what they'd do anyway
- Natural: the act of checking things IS the bake starting
- No new UI element needed

**Cons:**
- Ambiguous intent: user might be re-checking old progress while browsing (e.g., looking at what they completed yesterday)
- Hard to distinguish "accidentally tapped a checkbox" from "starting a new bake"
- No clear `startedAt` timestamp — do you start the timer on first check?
- Edge case: if the user unchecks everything, is the bake still active?

**Impact on composables:**
- `useProgress`: Would need a side-effect in `toggleItem`/`toggleState` to check if bake session exists and create one if not
- `useScratchpad`: Same as Option A, but triggered reactively when `hasProgress` becomes true

### Option C: Auto-detect from existing progress
**How it works:** If `hasProgress` computed (useProgress.ts line 141-143) returns true, bake is considered active. This already exists — `hasProgress` checks `Object.values(state.items).some(Boolean) || Object.values(state.states).some(Boolean)`.

**Pros:**
- No new trigger needed — completely derived state
- Handles page reload naturally (progress is already in localStorage, so `hasProgress = true` means bake is active)
- Simplest implementation

**Cons:**
- Can't distinguish "stale progress from yesterday's bake" from "active bake right now"
- No way to have browse-mode with progress visible (e.g., reviewing what you did last time)
- No `startedAt` — can't track bake duration
- "Reset Bake" becomes the only way to exit bake mode, and it destroys progress data

### Option D (hybrid): Explicit Start + Auto-resume
**How it works:** "Start Bake" button for fresh bakes. But if progress exists on page load, auto-resume the bake session (with optional confirmation banner — see AC5).

**Pros:**
- Clear intent for new bakes
- Handles reload gracefully
- Can distinguish fresh-start from resume

**Cons:**
- Still can't distinguish "came back to browse old progress" from "resuming yesterday's bake" without an explicit `startedAt`/`expiresAt`

## AC2: End-Session Mechanisms

### Option 1: Explicit "End Bake" button
**Where it lives:** Could replace/augment the "Reset Bake" button in RecipeMeta.vue (line 94-99). Currently "Reset Bake" (RotateCcw icon) only appears when `hasProgress` is true. An "End Bake" could appear when `bakeActive` is true.

**What happens to scratchpad data:**
- **Preserve for review:** `useScratchpad` data stays in `scratchpad-{recipeId}` localStorage. The scratchpad UI hides (bake mode off), but data persists until next `clearAll()` or explicit export-then-clear.
- **Export prompt:** On "End Bake", show a confirmation with "Export notes" (copies JSON to clipboard) and "End without exporting" options. This feeds into the `/feedback` workflow.
- **Progress data:** `recipe-progress-{id}` could either be preserved (so user sees completed state on next visit) or cleared alongside bake session end.

**Recommended flow:**
1. User clicks "End Bake"
2. If scratchpad has entries (`totalEntryCount > 0`): show confirmation "You have X notes. Export before ending?"
3. Export or dismiss
4. Set `bakeActive = false`, clear `bake-session-{id}` from localStorage
5. Scratchpad data stays in `scratchpad-{id}` for future `/feedback` sessions
6. Progress data: user's choice — keep visible or reset

### Option 2: Auto after last stage complete
**How it works:** When `completedStageIds.length === currentRecipe.stages.length` (all stages done), trigger end-session flow. The auto-advance system in `useProgress.ts` (`checkAutoAdvance`, line 66-84) already detects when all items+states in a stage are done.

**Pros:**
- Natural completion signal
- No extra button needed

**Cons:**
- Some bakes aren't "complete" when all stages are checked — user might still want to make notes during cooldown/cleanup
- Abrupt: user finishes last step and suddenly scratchpad disappears
- What if user un-checks a step after auto-end?

**Recommendation:** Auto-end should be a prompt, not automatic. When all stages complete, show a banner: "Bake complete! End session and export notes?" with Dismiss/Export options.

### Option 3: Timeout-based auto-end
**Not recommended.** Too unpredictable. Bakes can pause for hours (cold proof, waiting for oven). Would need a very long timeout (24h+) that's effectively useless.

## AC4: Persistence Strategy

### Current localStorage keys:
- `recipe-progress-{recipeId}` — items, states, stages (useProgress.ts line 26)
- `scratchpad-{recipeId}` — entries, generalNotes, dismissedReminders (useScratchpad.ts line 20)
- `last-recipe-id` — last loaded recipe (useRecipe.ts line 48)
- `photo-review:{recipeId}:{date}` — photo review state (PhotoReview.vue line 86)

### New key needed:
- `bake-session-{recipeId}` — bake session metadata

### Data shape for bake session:
```typescript
interface BakeSession {
  recipeId: string
  startedAt: string        // ISO timestamp
  active: boolean          // true while baking
  version?: string         // recipe version at bake start
}
```

### New composable vs fold into useProgress?

**Option A: New `useBakeSession` composable (RECOMMENDED)**
- Clean separation of concerns: progress = what's checked, session = are we baking?
- `useProgress` stays pure (checkbox tracking, auto-advance)
- `useBakeSession` owns: `startBake()`, `endBake()`, `isActive`, `startedAt`, `load()`, `save()`
- App.vue uses session state to conditionally create/expose scratchpad
- File: `src/composables/useBakeSession.ts`

**Option B: Fold into useProgress**
- Less file churn — one composable does it all
- But useProgress is already well-scoped and tested (progress.spec.ts has many tests)
- Adding session lifecycle bloats its API surface
- Mixing concerns: "what's checked" vs "are we baking"

**Recommendation:** New `useBakeSession` composable. It's a different concern and keeps both composables focused.

### Wiring in App.vue:
```
const session = useBakeSession(currentRecipeId.value)
session.load()

// Scratchpad only created when bake is active
watch([currentRecipeId, session.isActive], ([id, active]) => {
  if (id && active) {
    const sp = useScratchpad(id)
    sp.load()
    scratchpad.value = sp
  } else {
    scratchpad.value = null
  }
})
```

## AC5: Returning to In-Progress Bake

### Scenario: User is mid-bake, navigates away or reloads the page.

**What's in localStorage at that point:**
- `bake-session-{id}`: `{ active: true, startedAt: "...", recipeId: "..." }`
- `recipe-progress-{id}`: checked items/states
- `scratchpad-{id}`: captured notes/ratings

### Option A: Auto-resume (no prompt)
**How it works:** On recipe load, `useBakeSession.load()` reads `bake-session-{id}`. If `active: true`, automatically enter bake mode. Scratchpad and progress are already in localStorage.

**Pros:** Seamless. User reloads and picks up exactly where they left off.
**Cons:** If user navigated away intentionally (gave up, came back days later to browse), they're immediately in bake mode.

### Option B: Resume banner prompt (RECOMMENDED)
**How it works:** On recipe load, if `bake-session-{id}` has `active: true`:
1. Load progress normally (checkboxes restored)
2. Show a banner: "You started a bake on [date]. Resume?" with Resume / End buttons
3. If Resume: activate bake mode, load scratchpad
4. If End: clear bake session, keep progress visible, scratchpad stays in localStorage

**Pros:** Clear intent. Handles stale sessions gracefully.
**Cons:** Extra click to resume. But worth it for clarity.

**Banner placement:** Top of recipe content area, above RecipeMeta. Similar styling to ReminderBanner but full-width.

### Option C: Re-click Start Bake
**How it works:** "Start Bake" button is always available. If session data exists, clicking it loads existing data instead of starting fresh.

**Pros:** Simple — same button for start and resume.
**Cons:** User might not realize they have data from a previous session. Could accidentally start a new session and lose data.

### Staleness handling:
Add an optional `expiresAt` or check `startedAt` age:
- If `startedAt` is > 24 hours ago: treat as stale. Show resume banner with "(started yesterday)" context.
- If `startedAt` is > 7 days ago: show "You have an old bake session. Clear and start fresh?" prompt.

## AC6: Shared-Mode / QR Viewers

### Current shared-mode implementation:
- `ShareModal.vue` (line 36) generates URLs with `?shared=true` query parameter
- `BakeDetailView.vue` (line 105) detects `route.query.shared === 'true'`
- When `shared=true`: shows a welcome popover with reheat instructions
- After dismissing popover: removes `?shared` from URL and shows full bake detail
- Shared mode only applies to the bake-detail route (`/recipe/:id/bake/:date?shared=true`)

### Impact on bake session:
- **Shared-mode viewers land on bake-detail pages, NOT the recipe page.** The recipe page (with stages, checkboxes, scratchpad) is where bake mode lives. Shared viewers never see it.
- **No conflict:** The shared mode and bake session are on completely different routes. A QR scan goes to `/recipe/:id/bake/:date?shared=true` which renders `BakeDetailView.vue`. Bake session lives on `/recipe/:id` which renders the stages/StageCard template.
- **Browse mode IS the default for shared viewers** — they see the bake-detail view which is a read-only presentation of cook log data. No checkboxes, no scratchpad, no progress tracking.

### What about recipe page links?
If someone shares a direct recipe page link (not a bake detail link), the viewer would see the recipe page. Without bake session:
- Checkboxes would still work (useProgress is localStorage-per-browser, so viewer gets their own state)
- Scratchpad would NOT appear (bake mode off by default)
- This is the correct behavior: browse mode by default

### No changes needed:
The shared mode architecture is already on a separate route/view. The bake session lifecycle doesn't affect it at all.

## AC7: Written Recommendation

### Trigger: Explicit "Start Bake" button (Option A from AC1) with auto-resume (Option B from AC5)

**Rationale:** The scratchpad is a note-taking tool for active bakes. Making it appear only on explicit intent avoids clutter when browsing. The friction of one tap is minimal and provides a clear state boundary.

### Lifecycle Flow:

```
BROWSE MODE (default)
├── Recipe page loads → progress visible, scratchpad hidden
├── "Start Bake" button visible in RecipeMeta header
├── User taps "Start Bake"
│
BAKE MODE (active)
├── ScratchpadNote icons appear on steps
├── ReminderBanner appears above active steps
├── GeneralNotesFab appears bottom-left
├── Quick ratings available per step
├── "Start Bake" button replaced by "End Bake" button
├── Optional: bake timer shows elapsed time
│
│ [User checks items, captures notes, rates steps]
│ [Page reload → localStorage preserves everything]
│
├── All stages complete → prompt: "Bake complete! End and export?"
├── OR user taps "End Bake"
│
END BAKE FLOW
├── If scratchpad has entries → prompt: "Export notes before ending?"
├── Export copies JSON to clipboard (for /feedback)
├── Clear bake-session-{id} from localStorage
├── Scratchpad data preserved in scratchpad-{id}
├── Progress data preserved in recipe-progress-{id}
├── Return to BROWSE MODE
```

### Persistence:

| Key | Data | Lifecycle |
|-----|------|-----------|
| `bake-session-{recipeId}` | `{ active, startedAt, recipeId, version }` | Created on Start Bake, cleared on End Bake |
| `recipe-progress-{recipeId}` | `{ items, states, stages }` | Exists independently, persists across sessions |
| `scratchpad-{recipeId}` | `{ entries, generalNotes, dismissedReminders }` | Created on first note, persists until explicit clear or /feedback export |

### New composable: `useBakeSession`
- Owns the `active` state and `startedAt` timestamp
- Exposes: `startBake()`, `endBake()`, `isActive` (computed), `startedAt` (computed), `load()`, `elapsedMinutes` (computed, optional)
- Does NOT touch progress or scratchpad — those composables remain independent

### UX for each state:

| State | What user sees |
|-------|---------------|
| Fresh recipe, no history | Recipe page in browse mode. "Start Bake" button in RecipeMeta. |
| Active bake | All scratchpad UI visible. "End Bake" replaces "Start Bake". |
| Page reload mid-bake | Resume banner: "Bake in progress (started X min ago). Resume?" |
| Stale session (>24h) | Resume banner with context: "You started a bake yesterday. Resume or start fresh?" |
| After ending bake | Browse mode. Progress visible (checked items). Scratchpad hidden but data preserved. |
| Shared-mode viewer | Bake-detail page only — no scratchpad, no bake session, completely separate route. |

### Component changes needed:
1. **New file:** `src/composables/useBakeSession.ts`
2. **RecipeMeta.vue:** Add "Start Bake" / "End Bake" button (conditional on `bakeActive`)
3. **App.vue:** Wire `useBakeSession`, gate scratchpad creation on `session.isActive`
4. **New component:** `BakeResumeBanner.vue` — shown when returning to active session
5. **StateStep.vue, StageCard.vue:** No changes needed — they already gate on `scratchpad` prop being present/null
