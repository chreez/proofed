Architecture flow — combined capture at bake start

Automatic (no user action)
Manual (user input)
Data stored

Flow A: During Bake Session (live)

1
User starts bake — clicks first stage or "Start Bake"
Scratchpad reminder fires: "Kitchen temp (°F)?" manual
↓
2
Simultaneous: fetch outdoor weather
Browser calls Open-Meteo archive API for today's date + Austin coords.
No API key. No CORS issues. ~200ms. auto
↓
3
User enters kitchen temp — e.g., "72"
Scratchpad captures value + timestamp manual
↓
4
Both values stored in session
Indoor: bake_stats.bulk_ambient_temps[0] (from user input)
Outdoor: bake_stats.weather (from API, cached in localStorage) store

User sees one prompt. Weather fetch happens silently in background. Total friction: type one number.

Flow B: Backfill (past bakes via /bake-log)

1
Agent runs /bake-log session — user provides bake date
Agent knows the date from cook_log entry trigger
↓
2
Agent fetches weather for bake date
Script/composable calls Open-Meteo archive API for that date
Can batch: fetch entire month in one call for bulk backfill auto
↓
3
Weather written to cook_log entry
Stored in recipe JSON alongside existing bake_stats store

No indoor temp for backfill — that data is gone. Outdoor weather is always recoverable from the API.

Developer/Admin Perspective

What you set up once

// vite.config.ts — nothing needed // No API key, no env vars, no proxy // recipe.json — per recipe config "config": { "ambientTempTracking": { "required": true, "stages": ["FERMENT_BULK"] } } // composable useWeather(date, coords) → returns { daily, hourly, loading }

What happens at runtime

GET https://archive-api.open-meteo.com /v1/archive ?latitude=30.27 &longitude=-97.74 &start_date=2026-04-09 &end_date=2026-04-09 &hourly=temperature_2m, relative_humidity_2m, precipitation, cloud_cover, wind_speed_10m &temperature_unit=fahrenheit &timezone=America/Chicago → 200 OK, ~2KB JSON, ~200ms → CORS: Access-Control-Allow-Origin: * → No key required

Data Shape (cook_log entry)

{ "date": "2026-04-09", "bake_stats": { "bulk_ambient_temps": [ { "value": 72, "unit": "F", "timestamp": "2026-04-09T08:30:00" } ], "weather": { "source": "open-meteo", "fetched_at": "2026-04-09T08:30:05", "location": { "lat": 30.27, "lon": -97.74, "name": "Austin, TX" }, "daily": { "temp_high_f": 84, "temp_low_f": 62, "humidity_avg_pct": 55, "condition": "Partly Cloudy", "precip_mm": 0 } } } }

Minimal daily summary. Hourly array optional for future analysis. Weather block is sibling to existing bake_stats fields.

Why this works from the browser

Open-Meteo returns Access-Control-Allow-Origin: * on all endpoints. No API key, no proxy, no backend. The browser fetches directly.

Visual Crossing was the original spike recommendation but does NOT support CORS and requires an API key. Rejected for browser-side use.

Fallback: If Open-Meteo is down, weather field is simply absent. No error, no broken UX — the weather pill just doesn't render.
